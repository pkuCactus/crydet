## 2. 核心经验

### 2.1 LLM 的角色定位

在整个项目中，LLM 主要承担了以下角色：

**（1）架构设计师**

LLM 从初始的散落文件结构，设计出了清晰的模块化架构：

```
utils/       → 配置、日志统一管理
model/       → Transformer、Loss、EMA、调度器各司其职
dataset/     → 数据读取、增强、特征、采样器独立模块
configs/     → YAML 配置驱动，避免硬编码
scripts/     → 工具脚本独立目录
```

关键重构提交 `5570694`（2026-03-17）一次性将 config.py 移至 utils/、新增 logger/ema/scheduler/distributed 四个模块，完成了从"配置散落"到"架构清晰"的转变。这种大规模模块拆分是 LLM 的强项——它能在一次对话中理解全局依赖关系并生成完整的重构方案。

**（2）批量 Bug 猎手**

提交 `1c17e27`（2026-03-23）一次性修复了训练脚本中的 7 个 Bug：

| Bug | 描述 | LLM 如何发现 |
|-----|------|-------------|
| Bug1 | resume 时 epoch 循环从 0 重启 | 代码审查发现 range 起点硬编码 |
| Bug2 | EMA restore 无保护，异常时参数不还原 | 缺少 try/finally，LLM 补充 |
| Bug3 | 分布式 epoch_loss 被 world_size 放大 | 数学逻辑错误，LLM 推理发现 |
| Bug4 | step-based warmup 首批次 lr 错误 + global_step 未恢复 | 训练循环状态管理缺陷 |
| Bug5/6/7 | 冗余 if/else、best_model.pt 写两次 | 代码简化审查 |

LLM 的批量 Bug 发现能力来源于它对代码的全局理解——它不只是看单个函数，而是追踪状态在训练循环中的流转路径，发现逻辑漏洞。

**（3）性能优化顾问**

提交 `e4a3bc3`（2026-03-27）带来了显著的性能提升：

| 模块 | 优化手段 | 加速效果 |
|------|---------|---------|
| AudioReader | LRU 内存缓存 + 线程局部 librosa | 25x |
| FeatureExtractor | torch.compile + GPU-only 操作 | 22x |
| AudioAugmenter | 预生成噪声池 + 线程局部 sox | 减少 I/O 阻塞 |

LLM 不仅给出了优化方向（缓存、编译、并行），还直接生成了 benchmark 代码和性能分析文档，形成了完整的优化闭环。

**（4）调试合伙人**

DDP 死锁是本项目最棘手的问题，经历了 4 次迭代修复：

1. `2026-03-11 21:50` — 确保 schedule 长度一致
2. `2026-03-12` — 重新设计分布式采样器，直接分区而非包装
3. `2026-03-30 16:43` — `torch.cuda.synchronize()` 解决异步操作竞争
4. `2026-03-30 19:36` — 回退到稳定版本，确认 `synchronize()` 的必要性

LLM 在调试中的价值体现在：它能快速理解 NCCL/GPU 同步的底层机制，生成针对性的修复代码，但同时也暴露了一个局限——LLM 生成的优化代码（如 `torch.compile` 与 `all_reduce` 的冲突）可能引入新的问题，需要实际运行验证。

### 2.2 高效协作模式

**模式一：对话驱动的渐进式开发**

项目中最常见的模式是：人类提出需求 → LLM 生成代码 → 人类验证并提交 → 发现新问题 → 再次对话。这种循环在 git 历史中表现为同一日期密集的 Fix/Fix/Fix 序列：

```
03-11:  Fix → Fix → Fix → Fix → Fix（5次迭代修复维度和API兼容性）
03-12:  Fix → Fix → Fix → Refactor（DDP采样器3次修复后重构）
03-17:  Feat → Fix → Fix → Fix → Fix → Refactor（增强后连续修复边界条件）
03-30:  Fix → Fix → Fix → Revert（DDP死锁的4次尝试）
```

**模式二：大步重构 + 小步修补**

LLM 适合先做大规模架构重构（一次改 6-24 个文件），再通过小提交修补边界问题：

- `5570694`：重构架构，新增 6 个模块（12 files, 1970 insertions）
- `01598e6`：简化 train.py，重构配置体系（6 files, 200 insertions）
- 随后几天：Fix 提交修补配置错误、设备不匹配、除零等边界问题

**模式三：文档即设计**

LLM 的一大优势是"边写代码边写文档"。项目中的文档更新几乎与代码变更同步：

- 架构重构后 → 立即更新 CLAUDE.md
- 特征提取重写后 → 更新 feature_extraction_flow.md
- 性能优化后 → 生成 performance_analysis.md
- 数据增强文档 → 用 Mermaid 图表重构可视化

### 2.3 需要警惕的问题

**问题一：LLM 生成的优化可能引入新 Bug**

最典型的案例是 DDP 死锁：

- LLM 建议移除 `torch.cuda.synchronize()` 以减少同步开销
- 实际运行发现这导致 `all_gather` 异步操作竞争，训练卡死
- 最终回退到稳定版本 + 保留必要 synchronize

教训：LLM 对性能优化的建议需要**实际运行验证**，尤其是涉及并发/分布式场景。

**问题二：LLM 不理解运行时环境**

多次出现 PyTorch API 版本兼容性问题：

- `torch.amp.autocast` → 需要 `device_type` 参数（PyTorch 2.0+）
- `torch.cuda.amp.GradScaler` → API 变更
- `dist.init_process_group` → 需要 `device_id` 参数（PyTorch 2.6+）

LLM 倾向于使用最新 API，但项目环境可能不是最新版本。需要在对话中明确指定运行时版本。

**问题三：过度重构的风险**

提交历史中有一些"重构后回退"的模式：

- `0f73e91`：低能量样本过滤并行化 → 回退为串行（并行化引入了数据不一致）
- `da2e94d`：DDP 优化 → 回退到 `a2332e2`（优化引入死锁）

教训：对于已经稳定运行的代码，LLM 提出的重构建议应**增量验证**，而非一次性大改。

## 3. 实践方法论

### 3.1 项目启动阶段：让 LLM 快速建立全局视图

**做法：**

1. 创建 `CLAUDE.md` 文件，描述项目架构、数据流、关键设计约束
2. 让 LLM 基于设计文档直接生成模块代码骨架
3. 人类补充业务逻辑细节（如音频增强的具体参数、采样策略的业务规则）

**效果：**

- 03-11 一天完成模型+训练+评估+导出全流程（21 次提交）
- 架构从一开始就有清晰的模块划分，避免了后期的大规模重写

**关键约束在 CLAUDE.md 中的体现：**

- `Linear projection (NOT Conv1d patch embedding)` — 防止 LLM 使用常见但不适合的 Conv1d
- `Time dimension T=157 for 5s audio` — 明确输入维度
- `Mixup 规则：Cry 样本能量差 3-10 dB` — 业务规则约束

### 3.2 重构阶段：先明确目标，再让 LLM 执行

**做法：**

1. 人类明确重构目标（如"简化 train.py"），而非让 LLM 自行决定重构方向
2. LLM 提出重构方案（如配置体系重构、train.py 简化）
3. 人类审查方案合理性，确认后执行

**示例：train.py 的渐进简化**

```
03-23 19:01 Refactor: 简化 train.py 代码
03-23 19:15 Refactor: 简化 train.py 中的重复模式
03-23 19:31 Refactor: 将 scheduler.step 移到训练步骤前面
03-24 09:14 Refactor: Simplify train.py and restructure configuration
```

4 次提交逐步将 train.py 从臃肿的硬编码版本演进为配置驱动的清晰版本。

### 3.3 调试阶段：提供完整上下文，而非只描述症状

**做法：**

1. 提供 Bug 的完整上下文：错误日志、相关代码段、运行环境
2. 让 LLM 分析根因，而非猜测修复
3. 对 LLM 的修复代码进行实际运行验证

**示例：DDP 死锁调试**

提供给 LLM 的信息：训练卡住的位置、NCCL 日志、分布式采样器的代码、GPU 同步点的代码。LLM 基于这些信息分析了三个可能的根因（schedule 不一致、异步操作竞争、编译器冲突），逐一生成修复代码，最终通过运行验证确定了解决方案。

### 3.4 文档阶段：让 LLM 维护文档与代码的一致性

**做法：**

1. 每次架构变更后，让 LLM 同步更新 CLAUDE.md 和 docs/
2. 利用 LLM 的可视化能力生成 Mermaid 流程图
3. 文档作为代码审查的一部分，防止文档落后于代码

**效果：**

- 7 个技术文档覆盖了设计、增强、特征、推理、性能、训练优化
- Mermaid 图表使数据流可视化，降低了理解门槛

## 5. 反模式与教训

### 5.1 不要让 LLM 决定重构方向

LLM 倾向于"过度设计"——为未来可能的需求添加抽象层。本项目通过 CLAUDE.md 中的原则约束：

```
请使用第一性原理思考。你不能总是假设我非常清楚自己想要什么和该怎么得到。
请保持审慎，从原始需求和问题出发，如果动机和目标不清晰，停下来和我讨论。
```

### 5.2 不要盲目信任 LLM 的性能优化

LLM 生成的优化代码在单测中可能表现良好，但在实际分布式环境中可能引入新问题。**必须运行完整训练流程验证**。

### 5.3 不要省略运行验证步骤

项目中有多次"Fix → Fix → Fix"的迭代模式，这正是因为 LLM 生成的代码需要实际运行才能发现边界问题。如果省略验证步骤，可能会将 Bug 带入后续开发。

### 5.4 明确指定运行时环境

LLM 默认使用最新 API，但生产环境可能使用旧版本。在对话中应明确指定：

- PyTorch 版本
- Python 版本
- CUDA 版本
- 操作系统

### 5.5 利用 CLAUDE.md 作为约束合约

CLAUDE.md 是人与 LLM 之间的"约束合约"，它定义了：

- 架构约束（如 Linear projection NOT Conv1d）
- 业务规则（如 Mixup 能量差 3-10 dB）
- 关键参数（如 T=157、F=64/128/192）
- 代码规范（如 logging 替代 print）

每次架构变更后更新 CLAUDE.md，确保 LLM 在后续对话中遵循最新的约束。

## 6. 最佳实践清单

### 适合让 LLM 做的事

1. **模块拆分与架构重构** — LLM 理解全局依赖，擅长模块化
2. **批量 Bug 发现与修复** — LLM 追踪状态流转，发现逻辑漏洞
3. **配置体系设计** — LLM 生成 dataclass/YAML 配置体系高效
4. **文档编写与可视化** — Mermaid 图表、API 文档生成
5. **样板代码生成** — 训练循环、评估脚本、导出脚本等模式化代码
6. **性能瓶颈分析** — LLM 识别热点，提出优化方向

### 不适合完全依赖 LLM 做的事

1. **分布式训练调试** — NCCL/GPU 同步问题需要实际运行观察
2. **性能优化落地验证** — 必须在目标环境 benchmark
3. **业务规则细节** — 如 Mixup 能量差阈值、采样权重等需要领域知识
4. **运行时版本兼容性** — LLM 可能使用不兼容的 API

### 人与 LLM 的职责边界

| 职责 | 人类 | LLM |
|------|------|------|
| 需求定义与优先级 | 主导 | 辅助（提醒遗漏） |
| 架构方向决策 | 主导 | 提议（多方案对比） |
| 代码生成 | 审查+验证 | 主导生成 |
| Bug 修复 | 确认根因 | 批量发现+生成修复 |
| 运行验证 | 主导 | 不参与 |
| 文档维护 | 审查 | 主导生成 |
| 性能优化方向 | 确认目标 | 提议方向 |

### 7.2 CLAUDE.md 的结构建议

一个有效的 CLAUDE.md 应包含：

1. **项目概述** — 一句话描述项目目的
2. **架构图** — 目录结构 + 数据流
3. **关键约束** — 用 NOT/ALWAYS 等明确词标记
4. **数据结构表** — 关键数据结构的形状和含义
5. **配置参数表** — 所有可调参数的默认值和含义
6. **常见命令** — 运行/测试/导出命令
7. **反模式提醒** — 防止 LLM 重犯的错误

### 7.3 Git 提交规范

```

```

类型标签：`Feat`、`Fix`、`Refactor`、`Perf`、`Docs`、`Config`、`Breaking Change`、`Revert`

## 8. 总结

LLM 在 CryDet 项目中的核心价值是**加速从想法到可运行代码的转化**，而非替代人类的判断。具体表现为：

1. **架构搭建加速 7-10x** — 从设计文档到完整模块代码
2. **Bug 发现加速 10-20x** — 批量逻辑审查替代逐行排查
3. **文档同步 2-3x** — 代码变更后文档即时更新
4. **性能优化加速 3-5x** — 方向识别 + 代码生成 + benchmark

但 LLM 的局限同样明显：**它不理解运行时环境**，**生成的优化可能引入新问题**，**需要人类验证才能落地**。

最有效的协作模式是：**人类定义方向和约束 → LLM 生成方案和代码 → 人类验证并迭代**。这个循环中，CLAUDE.md 是关键的桥梁——它将人类的决策凝固为 LLM 可遵循的规则，防止 LLM 在后续对话中偏离既定方向。

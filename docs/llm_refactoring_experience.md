# 跨区重构经验：黄区梳理规划，蓝区重构实现

## 实践概览

| 问题 | 解答 |
|---|---|
| 您优秀实践的 DNA 是什么？ | **两段拆分 + 规格衔接 + 循环收敛**：黄区弱模型读真实代码提 spec（架构/流程/约束），蓝区强模型按 spec 做实现，CLAUDE.md 沉淀 NOT 规则等硬约束防止重复犯错，蓝区小数据开发、黄区大数据验证，反馈迭代直到收敛。人始终负责方向与判断。 |
| AI 生成代码量有多少？ | 重构后全部约 **1.3 万行 Python**（39 个文件，模型/数据/训练/评估/导出全链路）由蓝区强模型按 spec 生成，含 YAML 配置体系与文档；人写的是 spec、CLAUDE.md 约束和 review 判断。 |
| 工作量收益是多大？ | 体现在三个方面：① 批量 bug 审查从逐行排查一两天压到约一小时（单次体感）；② 数据加载、特征提取分别约 25×、22× 模块级提速（蓝区小数据下测得）；③ 改架构从改代码变为改 YAML 参数，多档端侧模型一套代码。端到端精度收益待黄区大数据验证。 |
| AI 能力有何不足之处，您是怎么应对的？ | 四类不足及对策：① 默认最新 API 与黄区旧环境冲突——版本钉进 spec/CLAUDE.md；② 并发/分布式优化小数据不暴露——必须走完整循环到黄区大数据验证；③ 不会判断哪些操作不能并行（数据一致性）——并行性由人裁决；④ 过度设计倾向——CLAUDE.md 加第一性原理/YAGNI 约束。本质是判断力缺口由人补齐。 |

---

在公司内网（黄区）做算法开发与重构，受两道墙夹着：原始代码不能出公司，内网可用的开源模型又弱又堵。出路是把重构拆两段：黄区模型提架构和规划，蓝区最新模型按规划完成实现——前一段轻量、弱模型够用，后一段要判断力、交给外部强模型。

这套做法在 CryDet（婴儿啼哭检测）项目上完整跑过一遍，下面把经验和踩过的坑整理出来。受合规和弱内网模型限制的团队，不必等内网追赶前沿，现在就能借外部强模型做算法重构，经验也能沉淀成规格与约束，跨区复用。

---

## 背景：黄区的局限

黄区是公司内网；蓝区是相对的叫法，指能访问外部强模型的开放环境。黄区两道墙都摆在明面上。

**第一道墙：原始代码和数据不能出公司。** 合规红线，没法直接拿去外部环境跑。这套跨区流程还有一个更具体的适用前提：**被重构的代码本身必须是非 KIA 级别**（公司密级分类中允许经内网模型提取抽象描述的级别）——KIA 级代码不进这个流程，太敏感，即便内网弱模型提取也有风险。非 KIA 代码可以由黄区弱模型读、提取 spec；spec 只留架构、流程、形状、约束这些抽象描述（不含源码、不含数据），能出公司交蓝区。

**第二道墙：可用模型只有 glm-5.1、deepseek-v4-flash 这类较弱的内网模型，两层短板叠加。** 一是判断力不够：算法重构（提速、提精度、改架构）要的是判断力不是算力，弱模型在架构设计、分布式调试、性能瓶颈分析这类多模块、长输出的任务上明显吃力。二是可用性不稳：用的人多，常卡、慢、中断，重度生成（一次产出几百行重构代码）一旦断了很难续上。

这类任务恰好是重构的核心，又都是长输出、重生成的任务——弱模型做不动，拥堵中断更让它雪上加霜。

## 为什么需要蓝区开发

蓝区能访问 kimi-3、gpt-5.6 sol、claude-fable 等外部强模型，经 codex / Claude Code 驱动。它补的是黄区缺的判断力，不是算力——算法重构里那些难的部分，恰好是弱模型做不对、强模型做得对的。下表用几类常见任务对照（都是公开可见的典型现象，不限于某个项目）：

| 任务 | 黄区弱模型 | 蓝区强模型 |
|---|---|---|
| 从设计生成模块骨架 | 倾向套训练数据里最常见的范式——比如一听"Transformer 做分类"就上 ViT 那套 Conv1d patch embedding + `[B,C,H,W]`，不管输入到底是不是图像 | 能按给定的约束（输入形状、投影方式、时序长度）生成贴合任务的骨架，多文件结构一次成型 |
| 分布式/并发调试 | 盯症状给表面修复——比如多卡训练卡住就加个 barrier，修一处漏一处 | 能跨模块读代码 + 日志，追到根因（缺失的同步点、异步 collectives 的竞争、compile 与通信库的交互） |
| 批量 Bug 审查 | 逐行找一两个明显问题 | 全局视角追踪训练循环里状态（lr 调度、EMA 恢复、loss 跨 rank 归约、step 计数）的流转，一次列出多个含数学/逻辑错的 bug |
| 性能瓶颈识别 | 单文件内看局部 | 跨数据加载/特征提取/增强多个模块读代码，定位 GIL 阻塞的外部进程调用、CPU 特征提取让 GPU 空转等热点 |

这几类正是算法重构的核心，也是弱模型最吃力的地方——要的是判断力和跨模块推理，不是多几个参数。

## 跨区协同的优势

既然蓝区强模型能做这些，为什么不直接把代码搬过去全交给它？两道墙挡着：代码不能出公司，外部模型也碰不到内网真实数据。搬代码不合规；光靠人手写描述喂给外部模型，又丢了内网模型能直接读真实代码的优势。出路是让两边各做擅长的一段：

- **黄区段（提取 + 规划）**：内网模型读真实代码，产出三样东西——项目的逻辑流程、当前架构、重构的 prompt 和规划步骤。只读只描述不写实现，恰好是弱模型能做到的；轻量任务，卡了断了重试续上即可；产出是抽象描述而非源码，能出公司。
- **蓝区段（执行 + 实现）**：外部模型拿到上述架构、流程和目标架构，直接做重构实现。这段要判断力和跨模块推理，是强模型的强项；它只碰 spec、碰不到内网真实代码和数据，合规也不破。

这套分工的好处：

1. **中间产物就是交接规格**。架构 + 流程 + 重构 prompt + 规划步骤，既是从黄区带到蓝区的输入，也是事后带回黄区复用的经验载体，同一份 spec 能驱动不同的蓝区模型。
2. **强模型可随前沿替换**。spec 是模型无关的——今天用 kimi-3，明天换 gpt-5.6 sol 或 claude-fable，输入不用改，前沿更新时只换执行端。

同时要记住一条限定：**经验需要落地验证，不能只听理论**。spec 和优化方向听起来都对，但跑起来才知道——有的优化真有效，有的反而破坏正确性。具体提速倍数见下文 CryDet 的落地结果，翻车案例见后文踩坑。

## 黄区梳理规划：怎么用弱模型做提取和规划

弱模型在这里的角色是"只读、只描述、不写实现"。把它当成一个能读代码的助手，按维度喂代码，让它产出结构化 spec。每个维度的输入是相关代码/配置，输出是可出公司的抽象描述（不含源码、不含数据）。下表是常用的拆法：

| 维度 | 输入（黄区真实代码/配置） | 让弱模型产出 | 输出 spec 形态 |
|---|---|---|---|
| 算法整体架构 | 顶层目录、入口脚本、模块间调用关系 | 梳理端到端流程：数据→特征→模型→训练→评估→导出 | 流程图 + 每环节职责一句话 |
| 模型架构 | 模型定义代码（forward、各层） | 还原网络结构：输入形状、卷积/时序块、池化、分类头（原始多为 CNN+LSTM） | 结构描述 + 张量形状流转 `[B,T,F]→…→[num_classes]` |
| 数据读取 | 数据集类、采样器、特征提取 | 还原 pipeline：文件扫描→切片→增强→特征→collate | 数据流图 + 每步张量形状 + 关键约束（能量过滤、mixup 规则等） |
| 模型训练 | 训练循环、loss、优化器、调度器、EMA | 还原训练逻辑：前向→loss→backward→step→EMA→验证 | 训练状态流转图 + lr/step/epoch 语义 |
| 输入输出设计 | 各模块的接口函数签名 | 抽出每个模块的输入/输出张量形状与含义 | 接口约定表：模块 \| 输入 \| 输出 |
| 重构方案 | 当前架构 + 重构目标（提速/精度/解耦） | 规划重构步骤与优先级，拆成可独立验证的小步 | 分步规划 + 每步目标 + 验收标准 |

一个示例（数据读取维度）：把数据集类和特征提取代码喂给弱模型，让它产出"文件扫描→按时长切片→能量过滤→增强→FBank 特征→collate 成 `[B,T,F]`"的数据流图，并标出每一步的张量形状和能量阈值、mixup 能量差这类约束。这份描述不含源码，能直接出公司交给蓝区。

几个让弱模型出对 spec 的技巧：

- **一次只喂一个维度**，别让它一次性"重构整个项目"——弱模型上下文和推理深度都不够，一次一个维度才出得对。
- **要形状和约束，不要代码**。形状和约束是抽象的，能出公司；源码不能。
- **让它复述关键约束**（如输入是 `[B,T,F]` 不是 `[B,C,H,W]`、用 Linear projection 不用 Conv1d）。复述错了正好暴露它没理解的地方，人纠正后直接写进 CLAUDE.md——这些纠正是 spec 之外最该沉淀的约束。
- **关键数字和规则要人抽查，回原始代码核对**。弱模型可能一本正经地误解老代码——而 spec 一旦错了，蓝区会忠实地实现成错误的代码，还能通过循环里"代码与 spec 一致"的核验，错得毫无痕迹。循环核验的是"实现 vs spec"，spec 与原始代码的保真度只有人能把关：形状、阈值、采样规则这类关键点，抽查几个回原文对一遍，成本不高，漏了代价很大。

**注意黄区段的"规划"是在人给定的重构方向下做任务拆解，不是自主架构设计。** 重构方向（迁 Transformer、多端部署这类决策）由人拍板，弱模型只负责把方向拆成可执行、可验证的步骤——拆解是模式化的轻活，方向判断才是它做不动的重活。这个分工与后文"重构方向决策由人判断"是一致的。

下面是针对**原始代码深度梳理**的具体 prompt 示例。原始项目是 TensorFlow + CNN+LSTM 的老代码，冗余多、历史模型变体多、没有版本注释——弱模型要先把这堆乱麻梳清楚，才能产出有意义的重构 spec。prompt 都按"非 KIA、只描述不贴源码"写好。

代码盘点示例（先搞清有什么，别急着看实现）：

```
这是一个 TensorFlow 写的音频分类老项目（CNN+LSTM），代码冗余多、历史模型变体多、没有版本注释。
请先做一次全仓库盘点，不要急着看实现细节。输出：
1. 目录结构和文件清单，按"数据/模型/训练/评估/部署/工具脚本/疑似废弃"分类
2. 哪些文件是历史变体或死代码（入口引用不到、import 不到）、哪些是当前在用的
   （从入口脚本和调用链反推——因为没有版本注释，只能靠引用关系判断）
3. 入口脚本和实际能跑通的调用链是什么
只盘点和归类，不贴源码，不猜实现。
```

当前模型架构提取示例（CNN+LSTM）：

```
从上一步盘点出"当前在用"的模型定义，还原 CNN+LSTM 的网络结构。
输出从输入到分类头的逐层描述，每层标明：类型（Conv/Pool/LSTM/FC）、输入输出张量形状
（注意 TF 的记法）、参数量、是否带 BN/Dropout。
重点说清 CNN 部分和 LSTM 部分怎么衔接（CNN 输出怎么 reshape 进 LSTM）、时序维度 T、特征维 F 各是多少。
只描述结构，不贴源码。
```

数据 pipeline 提取示例（TF）：

```
还原从音频文件到训练 batch 的完整 pipeline，基于 TF 实现（先说明用的是 tf.data / placeholder / feed_dict 哪种）。
输出数据流图：文件读取→分帧/切片→特征提取（Fbank/MFCC？参数多少）→增强→batch。
每步标明张量形状、采样规则、哪些状态在 epoch 间重建。
标出关键约束：cry 样本能量过滤阈值、正负样本比例。只描述，不贴源码。
```

训练逻辑提取示例（TF）：

```
还原训练逻辑：用的是 tf.session / Estimator / Keras 哪套？画出训练步的状态流转：
前向→loss→梯度更新→（如有）调度器→保存→验证。重点：loss 组成、优化器和初始 lr、
lr 有没有调度、有没有 EMA、checkpoint 存了哪些、resume 怎么恢复（还是根本没做）。
指出和"无版本信息"相关的隐患（哪些状态没存、哪些 baseline 没记录）。
```

冗余与历史模型梳理示例：

```
项目里有多个历史模型变体和重复逻辑。请梳理：
1. 列出所有模型变体（按文件/类名），标注差异（层数？通道？带不带 LSTM？）和推测的演进顺序
   （没有版本就靠调用关系、注释、命名猜）
2. 列出重复逻辑（多处特征提取、多处数据加载），标出哪些当前在用、哪些是冗余
3. 分"可安全删除"和"需确认后再删"两类
输出为表格，便于重构时清理。
```

重构到 Transformer 的规划示例（核心 spec）：

```
原始是 TF + CNN+LSTM，冗余多、历史模型多、无版本信息。重构目标：迁移到 PyTorch + Transformer，
便于多端侧平台部署（不同算力/内存档位）。请产出重构 spec，包含：
1. 目标架构：Transformer 编码器 + 分类头，输入 [B,T,F]，Linear projection（不用 Conv1d patch embedding），
   模型大小用层参数（d_model/n_layers）控制以适配多档端侧
2. 迁移映射：原 CNN 局部特征 → Linear projection + encoder，原 LSTM 时序建模 → encoder 自注意力；
   哪些原逻辑保留（特征方案、数据约束），哪些丢弃（历史变体、冗余）
3. 分步规划：迁数据 pipeline（TF→PyTorch）→ 迁模型 → 迁训练循环 → 补多档端侧配置，
   每步标验收标准（输出形状对齐、精度不低于原 CNN+LSTM baseline）
4. 必须守住的约束：特征方案不变（Fbank 参数）、数据约束不变（能量过滤、正负比例）、
   精度不低于原模型 baseline
只产出 spec 和规划，不写实现代码。
```

这些 prompt 跑完，每个维度会得到一份描述。下面是数据读取维度的真实节选（已脱敏），可以直观看到 spec 的粒度：

```
## 数据读取 spec（节选）
- 输入：单声道音频，重采样到 16kHz，切 5 秒定长段（不足右补零，长音频随机切片）
- 特征：FBank，n_mels=64，n_fft=1024，hop_length=512，fmin=250Hz，fmax=8000Hz
  → 输出张量 [T=157, F=64]（T=157 对应 5s @16kHz / hop 512）
- 能量过滤：cry 标签样本平均能量低于阈值则丢弃（阈值数值属敏感信息，以约束形式描述：
  "过滤后保留的样本应为人耳可辨识的啼哭"）
- 增强规则：cry 样本可与 cry 样本 mixup，混入样本能量须低于原样本 3–10 dB；
  非 cry 只能与非 cry 混
- 采样：每 epoch 重建切片 schedule，cry / 非 cry 按目标比例平衡采样
- collate：stack 成 [B, 157, 64]；标签映射 cry=1，other=0
```

对照一下这份节选的分寸：有形状、有规则、有参数含义，但没有一行源码，也没有敏感数值（能量阈值改写成约束形式）。蓝区拿到它就能写出正确的 Dataset 和 collate_fn——每个维度一份这样的描述，合起来就是完整可用的规格说明。

黄区全程只产出这种 spec，不写实现；拿到蓝区同步回来的代码后怎么验证闭环，见后文"蓝黄协同的循环流程"。

## 蓝区重构实现：怎么用好外部强模型

下面是蓝区段（执行 + 实现）驱动外部强模型时几条行之有效的做法，都来自 CryDet 实战。前六条是用好强模型的具体技巧，最后一条 CLAUDE.md 是贯穿全套协作的主线。

### 用 spec 驱动，而不是用需求驱动

蓝区强模型最忌讳"给个模糊需求让它自由发挥"。正确的输入是黄区产出的 spec——设计文档/架构/接口/规划。比如生成模型骨架时，把设计文档和明确约束一起喂进去：

```
按照设计方案，实现模型、训练脚本、评估脚本和导出脚本。
注意以下约束：
- 输入格式是 [B, T, F]，不是图像的 [B, C, H, W]
- 用 Linear projection，不要用 Conv1d patch embedding
- T=157 对应 5 秒音频 @16kHz，hop_length=512
- 需要支持 DDP 多卡训练
```

骨架一次成型，后续只补边界 bug。spec 越清晰，模型越不偏方向；给模糊需求，它就套训练数据里最常见的范式（这里就是视觉 Transformer 那套）。

要点：**强模型的输出质量取决于输入的 spec 清晰度。** 黄区多花时间把 spec 写清楚，蓝区省掉大量纠偏。

### 调试：喂完整上下文，别只描述症状

分布式死锁这类难问题，只说"多卡训练卡住"，强模型只能给表面修复（加个 barrier 之类），修一处漏一处。换成喂完整上下文：

```
训练在验证阶段的 _compute_auc_distributed 函数卡住。
相关代码：
- 训练脚本的分布式验证逻辑（附代码片段）
- _compute_auc_distributed 函数实现
- NCCL 日志显示卡在 all_gather 操作
- 运行环境：4 卡 GPU，PyTorch 2.6，CUDA 12.4

请分析根因，不要只给表面修复。
```

它能跨代码 + 日志追踪，一次定位到三个根因：schedule 不一致、all_gather 异步竞争、torch.compile 与 NCCL 冲突，再逐一修逐一验。

要点：**错误日志、代码片段、运行环境一起给，远比只描述症状有效。** 强模型能追踪状态流转，但得有足够输入。

### 写完别急着用，先让它自审一轮

代码写完，主动让强模型审查一遍"有没有 bug"。它以全局视角追踪训练循环里状态（epoch、lr、EMA、loss、step）的流转，一次能列出多个问题——含数学逻辑错（如分布式 epoch_loss 被 world_size 放大）、resume 恢复缺陷（epoch 循环从 0 重启、EMA 缺 try/finally）等。逐个找逐个修要一两天，一次性列出后约一小时（本项目单次的体感数字，量级供参考）。

要点：**代码完成后主动让强模型做一轮审查。** 批量发现远快于逐行排查。

### 性能优化：让它定方向 + 出代码，但验证分两段

让强模型分析训练流水线瓶颈，它能跨数据加载/特征提取/增强多模块读代码，定位热点（外部进程阻塞 GIL、CPU 特征提取让 GPU 空转、mixup 额外磁盘读取），并直接生成优化代码（LRU 缓存 + 线程局部 librosa、torch.compile + GPU-only 操作、预生成噪声池）。

但优化结果不能只靠单模块 benchmark。torch.compile 与 DDP 的 all_reduce/all_gather 冲突，单模块 benchmark 看不出来，要跑完整训练才暴露（见后文踩坑）。蓝区用小数据验"方向对不对、快不快"，真正的大数据规模验证在黄区。

要点：**强模型擅长定瓶颈方向和出优化代码，但优化必须跑完整流程验证，且小数据过了不代表大数据过。**

### 渐进式重构，一次只改一个维度

复杂模块（如 940 行的训练脚本）重构，每轮只改一个维度——去重复模式、提取公共逻辑、修正训练循环语义、重构配置体系——每步改完跑一遍验证，确认无问题再下一步。一步到位改多个维度，出问题没法定位是哪步引入的。

要点：**重构复杂模块，渐进式优于一步到位。** 每次一个维度，每步验证。

### 文档跟着代码一起改

架构变更后，立刻让强模型同步更新 CLAUDE.md 和 docs（目录结构、数据流、特征配置、流程图）。强模型写文档快，但跨对话不保留上下文，拖到后面补写成本陡增。

要点：**文档更新是代码变更的一部分，不是事后补充。**

### CLAUDE.md 是跨区复用的约束文档

CLAUDE.md 是这套协作里最关键的桥梁——每次新对话强模型自动读，拿到固定约束（用 codex 等其他工具时，对应各自的持久指令文件，如 AGENTS.md，作用相同）：

- 模型用 Linear projection，不用 Conv1d
- 输入维度 [B, T, F]，T=157
- Mixup 规则：Cry 样本混合能量差 3–10 dB，非 Cry 只能和非 Cry 混
- Audio cache 用 file mtime 而非 MD5 hash
- DataLoader persistent_workers=False（避免 DDP 死锁）

其中 NOT 规则直接防止强模型重复犯错。Conv1d patch embedding 是视觉 Transformer 的常见做法，对音频分类不合适——CLAUDE.md 标注 NOT Conv1d 后，后续不再出现。这份约束文档在蓝区沉淀，带回黄区直接复用，是循环里唯一跨对话、跨区存活的东西。

要点：**具体的 NOT 规则比泛泛描述有效得多。** `Linear projection (NOT Conv1d patch embedding)` 防止错误选择，而"使用线性投影"只描述了正确选择。

## 蓝黄协同的循环流程

跨区协作不是"黄区提一次 spec、蓝区实现一次就完"。两边的环境和数据差得很远：蓝区是本地开发机（i9-14900HX / 32G 内存 / RTX 4080 Laptop 12G），只能用开源 AudioSet 小批量数据做开发、优化和调试；黄区是 8 卡 16G V100、512G 内存的训练环境，跑的是完整 AudioSet + 自采 + 购买的内网数据，真正的大批量训练调优只能在那边做。两边形成一个循环：蓝区开发→代码同步黄区→黄区大批量训练调优→反馈→蓝区修复，如此收敛。

```
  ┌─── 黄区：弱模型读真实代码 → 产出 spec v1（架构/流程/接口/规划）
  │                          ↓
  │     蓝区：强模型按 spec 实现重构
  │     用开源小批量数据做开发、调优模型和训练效率、调试问题
  │                          ↓
  │     代码同步到黄区
  │                          ↓
  │     黄区：先核验代码实现是否与 spec 一致（接口/形状/规约）
  │     再在内网大批量数据上训练调优，发现问题、跑出指标、
  │     分析与原始代码的差异、规约问题
  │                          ↓
  │     反馈回蓝区（带一致性核验结果、训练问题、差异分析，不带源码）
  │                          ↓
  │     蓝区：按反馈优化、修复，更新 spec / CLAUDE.md
  │                          ↓
  └──── 收敛？指标达标、约束稳定 → 最终 spec + CLAUDE.md + 代码回黄区复用
```

关键点：开发和验证是分开的——蓝区管"能不能做对、能不能更快"（小数据验证方向），黄区管"在大数据上到底行不行"（真实规模验证）。spec 的归属也随阶段变化：首轮 spec 必须由黄区从真实代码提取（蓝区碰不到原始代码），进入迭代后则由蓝区随代码一起演进维护，收敛后再整体带回黄区。黄区拿到同步的代码后，优先核验实现是否与 spec 一致（接口、形状、规约对不对），再上大数据训练调优——先排除"代码本身就没做对"，再判断"做对了在大数据上行不行"，省得拿错的实现白跑大数据。两边各自只碰自己能碰的数据，又通过代码和反馈把结果接起来。一次性 spec 必然漏（版本兼容、分布式副作用、大数据才暴露的瓶颈），循环才补得上。带回黄区的是收敛后的 spec + CLAUDE.md + 代码，下次同类任务直接复用，不用从零再走一遍。

两个方向的流转都要走本组织的合规流程，这是前提不是可选项：spec 出区前经审批确认不含源码和敏感数据，蓝区代码进黄区走安全准入扫描。各组织流程不同，本文不展开——但"抽象描述能出区"是审批通过的结论，不是自己拍的判断，照搬这套模式前先确认自己组织的合规要求。

反馈包的写法和 spec 同理：只描述现象、指标和环境，不带源码和数据。一次黄区→蓝区的反馈大致长这样：

```
## 反馈（黄区 → 蓝区）
- 一致性核验：Dataset 输出 [B,157,64] 与 spec 一致；增强 pipeline 的 mixup 能量差
  实现为 2–8 dB，与 spec 的 3–10 dB 不符
- 训练问题：第 3 个 epoch 起 loss 周期性尖峰，怀疑与 schedule 重建有关
- 性能：数据加载占训练步耗时约 40%，num_workers=8 时 CPU 打满
- 环境：PyTorch 2.6，CUDA 12.4，4 卡
```

蓝区拿这份反馈就能定位和修复，全程没碰到一条内网数据。

## 在 CryDet 上的落地结果

下面是这次实践在 CryDet 上跑出的实际结果，测于蓝区小数据开发验证阶段。注意这些数字的效力范围：**它们是蓝区小数据下的模块级结果，证明"方向对、确实快"；大数据下的端到端数字需黄区验证后才能定论**——后文踩坑会说明，小数据过了不代表大数据过。黄区大数据训练调优的反馈已固化进 spec / CLAUDE.md。测量方式：蓝区本地开发机（i9-14900HX / 32G 内存 / RTX 4080 Laptop 12G），数据为开源 AudioSet 小批量，对比优化前后该环节的单样本平均耗时（数据加载、特征提取分开计时），不是端到端 epoch 时间。

- **训练效率**：数据读取加 LRU 内存缓存 + 线程局部 librosa，约 **25× 加速**（模块级，小数据）；特征提取用 torch.compile + GPU-only 操作，约 **22× 加速**（模块级，小数据）——两者把训练循环里 GPU 等 CPU 的空转消掉
- **架构优化**：从单文件训练脚本（940 行）拆为 model/dataset/utils/configs/scripts **五个职责分离模块**；模型大小由 YAML 层参数（d_model/n_layers/n_heads/d_ff）控制，而非固定 variant
- **数据读取处理优化**：增强器预生成噪声池 + 线程局部 sox，消除 mixup 时的额外磁盘读取和进程阻塞；音频缓存以 file mtime 校验（非 MD5 hash），避免每轮重算
- **模型/架构更新成本降低**：改架构只改 YAML 参数（Large/Medium/Tiny/Nano 同一套代码），新增尺寸或调整深度无需改代码、无需维护多份 variant 实现
- **精度**：设计目标 F1 ≥ 0.95，实测需在黄区大数据上验证，待验证后回填（含实测 F1/准确率及相对原 CNN+LSTM baseline 的提升）

要坦白这节的边界：目前落地的是**效率和可维护性收益**，端到端效果（精度）的证据还缺——这是本文证据链上待补的最后一环，也是"循环尚未收敛"的真实进度。

## 跨区协作的坑

### API 版本不匹配：强模型默认最新，黄区环境偏旧

这是跨区协作最典型的坑。蓝区强模型写代码时默认按最新 API 来，黄区真实环境往往滞后（项目环境是 PyTorch 2.6），一同步过去就报错：

- `torch.amp.autocast`：PyTorch 2.0+ 需要 `device_type` 参数
- `GradScaler`：API 在新版本里变了
- `dist.init_process_group`：PyTorch 2.6+ 需要 `device_id`

每次都是黄区一跑才发现，再回头让蓝区改。应对：把 PyTorch/Python/CUDA 版本钉进 spec 和 CLAUDE.md，蓝区强模型按目标版本写，别用最新 API。

### 强模型的优化，黄区大数据才暴露问题

强模型提议"减少 DDP 同步点"、移除 `torch.cuda.synchronize()`，理由（减少同步开销）理论上成立，蓝区小数据开发时也跑得欢；同步到黄区跑大数据训练，all_gather 异步操作和后续代码竞争，训练直接卡死，最后回退到优化前的稳定版本。torch.compile 与 NCCL 的冲突也是同一类——单模块 benchmark 看不出来，完整训练才炸。

这正是循环流程里"黄区验证"的价值，也是为什么黄区要先核验一致性再跑大数据：蓝区小数据过了，不代表黄区大数据过。应对：涉及并发和分布式的优化，必须走完整循环到黄区验证，不能只信蓝区小数据。

### 并行化不优于串行

强模型提议把低能量样本过滤从串行改并行（ProcessPoolExecutor），结果数据不一致，回退串行。数据一致性敏感的操作，强模型不会自动判断哪些能并行、哪些不能。应对：可不可并行由人判断，别全信强模型的"并行化提速"提议。

### 过度设计倾向

强模型曾提议给 loss 函数加 Strategy 模式的抽象基类，"便于未来扩展"。但项目只需 focal + label_smoothing + combined 三种 loss，工厂函数已够，Strategy 模式是多余抽象。在 CLAUDE.md 加约束抑制这个倾向：

```
请使用第一性原理思考。如果动机和目标不清晰，停下来和我讨论。
```

教训：**对强模型提出的抽象和设计模式，先判断当前是否需要。** YAGNI 在与强模型协作时尤其重要——它容易为当前不需要的灵活性加代码。

## 适用场景边界

### 适合交给蓝区强模型的

1. **按 spec 生成模块骨架** — 前提是黄区已产出清晰 spec
2. **批量代码审查发现 Bug** — 写完主动让它审一轮
3. **配置体系设计** — dataclass + YAML 生成规范高效
4. **技术文档与可视化** — 流程图、API 文档
5. **样板代码生成** — 训练循环、评估/导出脚本等模式化代码
6. **性能瓶颈分析与优化方向** — 识别热点快，但只到"方向 + 代码"，验证交给黄区大数据

### 不适合完全交给强模型的（留黄区或人）

1. **分布式训练调试** — NCCL/GPU 同步问题要实际运行，且黄区大数据才暴露
2. **性能优化的最终验证** — 蓝区小数据过不代表黄区大数据过
3. **业务规则细节** — Mixup 能量差阈值、采样权重等需领域知识，在 spec 钉死
4. **运行时版本兼容性** — 黄区环境偏旧，版本钉进 CLAUDE.md
5. **重构方向决策** — 哪些值得重构、哪些不宜动，由人判断，别让强模型替你决定
6. **黄区段的提取与规划** — 弱模型能做，且要读真实代码，强模型碰不到

最后算一笔账，免得误读：这套流程省的是**模型能力的门槛**，不是**人力**。黄区核对 spec 保真度、逐轮整理反馈、裁决方向和并行性，都是人的判断时间，项目越复杂、循环轮数越多，人的投入越大。它适合的场景是"内网模型确实做不动这类任务、而人有领域判断能力但缺强模型入口"——用人的判断把两边的模型接起来，而不是把人从流程里摘出去。

规模上也要校准预期：本经验来自千行级、边界清晰的单项目。换成十万行级的祖传代码库，提取维度更多、弱模型上下文更吃紧、人的核对成本和循环轮数都会显著上升——思路不变，但建议先挑一个子系统试点跑通一轮循环，再决定要不要铺开。

## 总结

一句话：**黄区弱模型提 spec，蓝区强模型做实现，人负责方向与判断，CLAUDE.md 是跨区复用的约束，循环收敛。**

- 有 spec，强模型才能把设计变代码；给模糊需求就套常见范式偏方向。
- 有完整上下文，强模型才能有效调试；只描述症状只能猜。
- 有黄区大数据验证，强模型才能安全优化；蓝区小数据过不代表大数据过。
- 有 CLAUDE.md 的 NOT 规则，强模型才不重复犯错；具体约束比泛泛描述有效。
- 有人的方向判断，强模型才能正确执行；不宜让它替人决定重构什么、能否并行。

跨区不是一次性交接，是循环——蓝区小数据开发、黄区大数据验证、反馈修正 spec，直到收敛。带回黄区的不是某次实现的代码，是收敛后的 spec + CLAUDE.md + 代码，下次同类任务直接复用。

# 外部强模型重构内部代码：规格驱动 · 强弱分工 · 循环收敛

> 概述：当"能读内部代码的模型判断力不足、判断力充足的模型又读不到内部代码"时，用**规格（spec）**桥接两端。弱模型读真实代码提 spec，强模型按 spec 实现，人补判断缺口。出错后沉淀为 NOT 规则防重复犯错，小数据开发→大数据验证→反馈，循环至收敛。

## 范式内核与可推广性

将 LLM 用于公司内部代码重构时，普遍受制于同一道能力鸿沟：

- **能直接读取内部代码的模型（内网部署 / 本地可达），判断力往往不足**——架构设计、分布式调试、性能瓶颈定位、批量缺陷排查等多模块、长推理任务难以胜任；
- **判断力充足的强模型（外部前沿模型），又无法触达内部代码与数据**，受限于合规墙、网络隔离、数据不出域等约束。

本范式的核心，是以**"规格"桥接两端**：弱模型仅负责理解并提取抽象规格（不含源码、不含数据，可出域）；强模型依据规格完成实现，全程不接触内部代码与数据；由人补齐判断力缺口（方向决策、规格保真、并行性裁决）。该范式不绑定特定模型或项目。**适用判据是存在"能力差"**：弱模型可触达代码、强模型不可触达代码（通常源于合规墙/网络隔离/数据不出域）。若无此能力差，强模型可直接读码实现，规格驱动退化为普通的"写 spec 让模型实现"。

### 环境映射

| 本文术语 | 抽象含义 | 常见等价形态 |
|---|---|---|
| 黄区 | 模型可读代码，但合规/网络受限的环境 | 公司内网、数据不出域环境、本地部署 |
| 蓝区 | 可调前沿强模型，但不可触达内部代码的环境 | 外部开放网络、云端大模型、第三方 API |
| KIA（关键核心资产） | 仅可由内部大模型处理、不可进入本流程的最高密级 | 各组织的最高密级资产，按本组织密级表替换 |

> 合规判据：凡涉及所在组织禁止任何外部模型处理（即便仅提取规格）的密级，不进本流程。先用本组织密级表替换上表的 KIA/黄/蓝映射，再判断是否适用。快速自检：代码涉及客户隐私、金融核心账务或受监管密级数据时，默认按 KIA 处理，不进本流程，除非合规允许脱敏后提取规格。

### 四要素

| 要素 | 谁来做 | 产出 | 为什么这样切 |
|---|---|---|---|
| **分工** | 弱模型读、强模型写、人判断 | 规格 + 代码 | 代码理解属轻量任务，弱模型可胜任；实现需判断力，交由强模型；方向与保真属重量级判断，需由人承担 |
| **规格（spec）** | 弱模型从真实代码提取 | 架构/流程/接口/约束的抽象描述 | 不含源码→可出域；驱动实现；沉淀复用；模型无关（更换前沿模型仅需替换执行端） |
| **约束（CLAUDE.md/AGENTS.md 等）** | 人纠正 + 强模型沉淀 | 具体 NOT 规则 | 跨对话、跨区存活，防止强模型重复犯错（如"NOT Conv1d"） |
| **循环** | 小数据→大数据→反馈 | 收敛后的 spec+约束+代码 | 一次性规格必然有遗漏（版本兼容、分布式副作用、大数据瓶颈），需通过循环补齐 |

### 适用前提（五条并列，缺一不可）

> - [ ] 目标为判断力密集型重构（架构选型/分布式（ML 分布式训练、非 ML 并发与分布式系统）/性能瓶颈/批量排查等跨模块判断点 ≥2；"判断点"=需跨 ≥2 个模块/文件做因果推理才能决策之处）；
> - [ ] 可触达代码的模型判断力不足（最小子任务实测无法一次完成——单轮对话内产出的代码无法通过最小验证：编译、测试、形状对齐；或公开 benchmark 与前沿差距显著，如解决率相差 ≥2 倍；本领域无等价基准时以最小子任务实测为准。注："最小子任务"=能独立验证正确性的最小代码变更单元）；
> - [ ] 判断力充足的模型无法触达代码（合规墙/网络隔离/数据不出域）；
> - [ ] spec 可被弱模型干净提取且不含源码与敏感数据、可出域；
> - [ ] 具备对应规模的验证环境与有领域判断力的人（能独立裁决下列至少两类：spec diff 是否忠实于代码语义、操作能否并行、抽象是否过度、运行时版本兼容性）。
>
> 满足全部即可进入最小试点（见 §推广）。

## 循环流程：开发与验证分离

开发与验证分离：开发在可调强模型的小数据环境（合成/公开小样本，非敏感、可出域，只验形状与速度），验证在真实数据的大数据环境，两端以代码与反馈衔接，真实数据始终留黄区。

"小/大数据"对本项目指 ML 训练数据规模；非 ML 场景对应"低成本可调强模型环境 / 真实规模验证环境"，如本地小流量验证对应生产压测、单元测试对应端到端回归。

```mermaid
flowchart TB
    P["黄区 · 提取 spec（首轮）<br/>弱模型读真实代码"] --> A
    A["小数据环境 · 开发调优<br/>可调强模型·验可行性与速度"] --> B["代码同步 → 大数据环境<br/>走安全准入扫描"]
    B --> C["大数据环境 · 一致性核验<br/>代码 vs spec（小脚本）"]
    C --> C2["大数据环境 · 规格保真复核<br/>spec vs 真实语义（人审 diff）"]
    C2 --> D["大数据环境 · 大数据训练调优<br/>跑指标·暴露分布式/规模问题"]
    D --> E{"收敛?<br/>指标达标·约束稳定·反馈递减"}
    E -- 否 --> F["反馈回小数据环境<br/>现象·指标·环境（不带源码数据）"]
    F --> A
    E -- 是 --> G["收敛终点<br/>spec + CLAUDE.md + 代码 回域复用"]
```

非 ML 对照：①开发（本地小流量/单元测试）→ 代码同步（走准入扫描）→ 一致性核验（接口/形状对齐脚本）→ 保真复核（人审 spec diff）→ 真实规模验证（全量压测/端到端回归）→ 收敛？

开发（能否实现正确、能否更快）与验证（大数据上是否可行）分离；先核验实现是否与 spec 一致（排除"代码本身未实现正确"），再上大数据，避免以错误实现空跑一轮大数据。

核验分两类，不可混用：
- **代码–spec 一致性（轻、可脚本化）**：形状、接口跑个小脚本对齐，成本远低于直接上大数据空跑一轮。
- **spec–真实 保真（重、需人）**：spec 一旦在迭代中漂移，一致性核验照样通过却失真。故每轮反馈修改 spec 后，由人复核 spec diff 是否仍忠实于原始黄区提取（及真实代码语义）。保真这一环须由人复核；自动化一致性工具（如 OpenAPI/proto 校验）可辅助，但不替代人对语义漂移的裁决。

**spec 归属随阶段切换**：首轮 spec 由黄区弱模型提取并审批出域；进入迭代后，spec 的修改在蓝区由强模型提出、人裁决，收敛版本回域复用。spec diff 回域须走与首轮相同的出域复审。

反馈包与规格同理，仅描述现象、指标与环境，不含源码与数据。示例如下：

```
## 反馈（黄区 → 蓝区）
- 一致性核验：Dataset 输出 [B, 157, 64] 与 spec 一致；mixup 能量差实现为 2–8 dB，与 spec 的 3–10 dB 不符
- 训练问题：第 3 个 epoch 起 loss 周期性尖峰，怀疑与 schedule 重建有关
- 性能：数据加载占训练步耗时约 40%，num_workers=8 时 CPU 打满
- 环境：PyTorch 2.6，CUDA 12.4，8 卡集群取 4 卡调试
```

非 ML 反馈包示例（Web 服务，结构相同）：

```
## 反馈（内网 → 外网）
- 一致性核验：订单服务输出字段与 spec 一致；幂等键实现为"先查后插"，与 spec 的"INSERT ... ON CONFLICT"不符
- 压测问题：QPS 800 起数据库连接池耗尽，怀疑未复用事务
- 性能：热点接口 P99 420ms，占整体耗时约 60%
- 环境：Go 1.22，PostgreSQL 16，4 节点集群取 1 节点压测
```

两个方向的流转均须遵循所在组织的合规流程（此为前提，非可选项）：

- **出区审批**：spec 出区前经审批确认不含源码和敏感数据。
- **敏感分级**：模型架构与公开超参视为非敏感；数据阈值、业务规则数值、自采/购买数据标签属敏感，须脱敏或不出域。脱敏后 spec 可操作性下降（数值缺失），由黄区人审时在实现侧单独补入、以占位符标记。
- **入区扫描**：蓝区代码进黄区走安全准入扫描。

## 落地案例：CryDet 婴儿啼哭检测重构

本范式在 CryDet 项目上完成了从梳理、实现到黄区大数据验证的完整闭环，循环已收敛。

### 背景

原始项目为 TensorFlow + CNN+LSTM 遗留代码：训练逻辑集中于单个过大文件（冗余多、无注释）、历史模型变体繁多。目标：重构代码结构并演进模型至 Transformer 多档变体（Large/Medium/Tiny/Nano，基于 PyTorch），以支持多端侧平台部署（不同算力/内存档位），同时提升精度/效率、降低维护成本。

### 重构前后对照

| 维度 | 原始（TF + CNN+LSTM） | 重构后（PyTorch + Transformer） |
|---|---|---|
| 代码结构 | 训练逻辑聚于单个过大文件（冗余、无注释） | model/dataset/utils/configs/scripts **多模块职责分离** |
| 模型档位 | 固定 variant、多份实现 | YAML 层参数控制，**Large/Medium/Tiny/Nano 一套代码** |
| 模型演进 | 改架构=改代码、维护多份变体 | 改架构只改 YAML 参数，新增尺寸无需改代码 |
| 训练可观测 | 无统一可视化 | **TensorBoard 记录 loss/acc/lr/验证指标**，可视化调优闭环 |
| 数据管线 | 串行、无缓存、额外磁盘读取 | LRU（Least Recently Used）内存缓存 + 线程局部 librosa/sox + 预生成噪声池 |
| 代码来源 | 人写 | **约 1.3 万行 Python / 39 文件**（核心代码约 0.7 万行 + 测试/脚本约 0.6 万行，按目录估算）由强模型按 spec 生成初版、经人审改定稿；人写 CLAUDE.md 约束并做 review 判断（spec 由弱模型提取、人审保真） |

### 工作量与收益（分层归因）

> **重构工作量从预估 7–8 人月降至 1 人月**（7–8 人月为重构前按模块任务分解的估工；1 人月含人工 spec 保真、反馈整理与裁决时间）。须区分两层因果——**范式自身贡献**与**强模型能力产出**。

| 归因 | 收益 | 说明 |
|---|---|---|
| **范式·准入** | 在合规墙下使强模型可参与内部代码重构任务 | 跨区分工 + spec 出域使强模型"够得着"任务（全程不触达内部代码与数据） |
| **范式·保真** | 迁移后 Transformer 与原 CNN+LSTM 同等精度（F1≈0.92，达最低验收档） | spec 保留 Fbank（mel 滤波器组）/能量过滤/mixup 等约束 + NOT 规则防错 + 通用基线测试兜底（三者贡献无法分离测量） |
| **强模型能力** | 重构编码工作量下降（7–8→1 人月）、后续模型演进成本下降（YAML 参数化）、训练可视化调优、训练 epoch 4× 提速 | 强模型生成与调优能力承接编码劳动，人力转向判断；4× 提速含 TF→PyTorch 框架迁移贡献，与强模型编码贡献未分离 |

落地指标如下。端到端精度与训练效率以黄区完整训练为准；模块级微基准仅用于开发期方向验证，不作为对外提速指标——其易受缓存命中/单样本口径影响，不可外推端到端。

| 指标 | 结果 | 测试条件 |
|---|---|---|
| 端到端精度 | 迁移后 Transformer 与原 CNN+LSTM **同等精度 F1≈0.92**（两版均在黄区完整数据上训练），达到设计文档最低验收档（微型档，即 Tiny，F1≥0.92）目标 | 黄区完整数据（AudioSet+自采+购买） |
| 训练效率 | 单位 epoch **2h → 0.5h**，约 **4× 加速** | 同数据同硬件；2h=原 TF+CNN+LSTM、0.5h=迁移后 PyTorch+Transformer|

迁移后精度与原 CNN+LSTM 同等（F1≈0.92，达最低验收档），保真目标达到；训练效率、可维护性、可视化调优为收益项（提速含框架迁移贡献，见归因表）。

### 跨区分工映射

| 阶段 | 环境 | 执行方 | 产出 |
|---|---|---|---|
| 提取规划 | 黄区 | 弱模型读真实代码 | spec：流程/架构/接口/约束 |
| 实现调优 | 蓝区（开发机） | 强模型按 spec 实现 | 约 1.3 万行代码 + CLAUDE.md |
| 大数据验证 | 黄区（8 卡 V100/512G 内存） | 黄区训练（人监控） | 同等精度 F1≈0.92（达最低验收档）、分布式/规模问题 |
| 反馈收敛 | 蓝区→黄区循环 | 强模型修复、人裁决 | 收敛 spec+约束+代码回域复用 |

## 关键做法

| # | 做法 | 要点与原理 |
|---|---|---|
| 1 | **spec 驱动，不给模糊需求** | 把架构/接口/约束一起喂进去（本项目："输入 `[B, T, F]` 不是 `[B, C, H, W]`、用 Linear projection 不用 Conv1d"；通用："事务接口须幂等""错误码集中枚举""不允许引入新外部依赖"）。**原理**：强模型输出质量取决于 spec 清晰度，模糊需求会使其套用训练数据中最常见的范式而偏离方向 |
| 2 | **调试喂完整上下文** | 错误日志 + 代码片段 + 运行环境一起给，不只描述症状。**原理**：强模型能跨代码与日志追踪状态流转，但需足够输入 |
| 3 | **写完先让它自审一轮** | 代码完成主动让强模型查 bug（单次/小样本体感，未做对照测量）。**原理**：批量发现远快于逐行排查，一次列出多个含数学/逻辑错误的 bug |
| 4 | **优化定方向+出代码，验证分两段** | 强模型定位热点并出优化代码；小规模验方向、全规模验真实副作用（双环境只是其一实例，单环境可用分桶小/大数据替代；非 ML：小流量/全量压测、单元测试/端到端回归可替代双环境）。**原理**：单模块 benchmark 看不出分布式副作用，必须跑完整流程 |
| 5 | **渐进式重构，一次一维** | 复杂模块每轮只改一个维度，每步验证再下一步。**原理**：一步到位改多维度，出问题难以定位由哪步引入（通用工程原则，本范式下尤需坚持——多维度变更叠加 AI 生成更难定位根因） |
| 6 | **文档跟着代码一起改** | 架构变更立刻同步项目级约束文件/docs（不限于 CLAUDE.md/AGENTS.md）。**原理**：强模型跨对话不保留上下文，延后补写成本更高 |
| 7 | **重构前先建行为基线测试** | 黄金用例/输出快照/精度基线先行，每轮循环跑回归，绿了再上大数据（非 ML：契约测试/行为快照基线先行）。**原理**：AI 生成代码常表面正确、边界错（off-by-one、padding 方向、归一化口径）；基线测试是保真的自动化兜底 |

> 强模型相对弱模型有三点优势，这也是选它完成实现的原因：
>
> - 按约束生成贴合任务的骨架，而非套用训练数据中最常见的范式；
> - 跨模块读代码与日志，追踪状态流转与根因；
> - 以全局视角一次列出多个缺陷、跨多模块定位性能热点。
>
> 上述判断有公开基准佐证：SWE-bench（Jimenez et al., 2024）是公开多文件真实 bug 修复基准，其上头部模型解决率高于小参数模型（差距见公开榜单）；长上下文抓不稳中间信息（"lost in the middle"，Liu et al., 2023）、长输出到一半截断后无法续接，亦是社区反复讨论的老问题。这些现象落在重构任务上，即弱模型难以胜任、强模型能够胜任的几类工作。须说明：SWE-bench 度量的是 bug 修复，规格驱动从零生成无等价公开基准，故上述为类比推断而非直接证据。

## 核心机制：CLAUDE.md 跨区复用约束

每次新对话，强模型自动读取 CLAUDE.md 获取固定约束（使用 codex 等工具时对应各自的 AGENTS.md，作用相同）。其中 **NOT 规则**直接防止重复犯错。本项目样例：

- 模型用 Linear projection，**NOT** Conv1d patch embedding
- 输入维度 `[B, T, F]`，T=157
- Mixup：Cry 样本混合能量差 3–10 dB，非 Cry 只能和非 Cry 混
- Audio cache 用 file mtime，**NOT** MD5 hash
- DataLoader `persistent_workers=False`，避免 DDP 死锁（DDP 即 DistributedDataParallel）

**NOT 规则分类法**（便于他团队按类别沉淀，而非照搬上述项目样例）：

| 类别 | 本项目样例 | 通用判据（你的项目该写什么） |
|---|---|---|
| 架构选型 | NOT Conv1d patch embedding | 强模型易套训练数据中常见范式而易错处 |
| 形状/维度 | `[B, T, F]`，T=157 | 全局固定常量，跨模块须一致 |
| 领域阈值 | mixup 3–10 dB | 需领域知识、强模型无从得知的数值 |
| 实现细节 | mtime NOT MD5 | 性能/正确性敏感的实现选择 |
| 运行时行为 | persistent_workers=False | 与运行环境强耦合、出错才知的约束 |

沉淀一条 NOT 规则的最小步骤：现象 → 根因 → NOT 表述 → 入 CLAUDE.md。该约束在蓝区沉淀并带回黄区直接复用，是循环中**唯一跨对话、跨区存活**的产物。**具体的 NOT 规则比泛泛描述有效**——`Linear projection (NOT Conv1d patch embedding)` 防止错误选择，而"使用线性投影"只描述了正确选择。

## 风险与规避

| 风险 | 现象 | 根因 | 对策 |
|---|---|---|---|
| **API 版本不匹配** | 代码同步过去直接报错或行为悄悄变 | 强模型默认最新 API，目标环境偏旧（如 CUDA 11.x vs 12.x、Python 3.8 vs 3.11、依赖大版本断裂） | 把框架/语言/CUDA 版本钉进 spec 和 CLAUDE.md，按目标版本写 |
| **优化小数据过、大数据失效** | "减少 DDP 同步点"、移除 `cuda.synchronize()` 小数据正常通过、大数据训练卡死（非 ML：移除锁/改异步，小流量正常、全量压测现数据竞争/死锁） | all_gather 异步竞争、torch.compile 与 NCCL（NVIDIA 集合通信库）冲突，单模块 benchmark 看不出 | 涉及并发/分布式的优化必须走完整循环到大数据验证 |
| **并行化不优于串行** | 低能量过滤改并行导致数据不一致（非 ML：批量异步写致顺序依赖断裂） | 数据一致性敏感操作，强模型不会自动判断哪些能并行 | 按判别边界裁决：无共享可变状态/幂等/独立样本→可并行；共享 schedule/采样顺序/累积统计/跨样本一致性→须串行或加锁 |
| **过度设计倾向** | 给 loss 加 Strategy 模式抽象基类"便于未来扩展"（非 ML：给查询加多余仓储抽象、给接口加未用扩展点） | 项目只需三种 loss，工厂函数已够 | CLAUDE.md 加第一性原理/YAGNI 约束；先判断当前是否需要 |
| **生成代码表面正确、边界错** | 输出形状对、整体能跑，但 off-by-one、padding 方向、归一化口径错 | 强模型按常见范式实现，边界细节易偏 | 重构前建行为基线测试（黄金用例/快照/精度基线），每轮跑回归兜底 |

这些风险集中在版本、并行、抽象、边界几类判断上，强模型做不了，需人来判。

## 适用边界

**适合交由强模型的：** ①按 spec 生成模块骨架（前提：已产出清晰 spec）；②批量代码审查查 bug；③配置体系设计（按目标栈惯例，如 dataclass+YAML / struct+toml / 注解+properties）；④技术文档与可视化；⑤样板代码生成；⑥性能瓶颈分析与优化方向（只到"方向+代码"，验证交大数据）。

**能力上无法胜任、需人判断的：** ①分布式/并发调试（要实际运行才暴露死锁、竞争；ML 为分布式训练，非 ML 为并发系统）；②性能优化最终验证（小规模过≠全规模过；ML 为小数据 vs 大数据，非 ML 为小流量 vs 全量压测）；③业务规则细节（ML 如 mixup 能量差、采样权重；非 ML 如幂等键、事务边界、权限规则，须在 spec 钉死）；④运行时版本兼容性（环境偏旧，版本人钉）；⑤重构方向决策（哪些值得动、哪些不宜动，由人判断）。

**合规上无法触达、仅限内部的：** 提取与规划阶段——要读真实代码，强模型物理上不可触达；这段弱模型本身也可胜任。

**成本边界**：本范式降低的是模型能力的门槛，人力则从编码转向判断——编码由强模型承接（故 7–8→1 人月），但规格保真、反馈整理、方向与并行性裁决仍需人的判断，项目越复杂、循环越多，判断投入越大。本范式适用于"内部模型难以胜任、人有判断力但缺强模型入口"的场景，由人把两端能力接起来。

**方案对照**（基于弱模型在最小子任务上的实测表现推断，未做整项目对照实验；结论随弱模型版本而变，换版本须按 §适用前提第二条重测）：若改用本次所用的弱模型版本完成重构，依其已知的长上下文丢失、常见范式套用问题，预期在两端受阻——长段重构代码生成易中途中断、续接时上下文已丢失；架构层面倾向套用最常见的视觉 Transformer（ViT）范式，将 Conv1d patch embedding 错误用于时序音频。影响的不仅是效率，更关系到代码能否跑通。ViT 套用为本项目实例性推断；非 ML 场景弱模型的常见错误范式各异，如 Web 后端弱模型倾向套 CRUD 模板、忽略事务边界。

**适用规模**：本经验源自一个边界清晰的单项目（原始为完整 TF 项目、重构后约 1.3 万行多模块）。面对十万行级遗留代码库，提取维度增多、弱模型上下文更紧张、人工核对成本与循环轮数均会上升——思路不变，但建议先选取一个子系统试点跑通一轮循环，再决定是否全面铺开。

---

## 推广：最小试点与退出条件

照搬前先跑一个最小闭环，验证本组织是否适用：

- **试点规模建议**：单模块、≤2k 行、≤5 轮循环。
- **启动前置**：承接 §适用前提五项 + 一个有领域判断力的人 + 可调强模型通道 + 两个可隔离环境（或单环境分桶）。
- **每轮收敛判据**（各给可计量代理指标；阈值源自本项目实测，仅作起始参考，试点后据本组织数据校准）：
  - ①指标达标率 = 本轮验收指标达标项数 / 总项数，阈值建议 ≥80%（非 ML 场景"验收指标"对应测试通过率/性能基准达标项/回归基线保留项，按项目自有验收口径计数）；
  - ②约束稳定度 = 本轮约束文件（CLAUDE.md/AGENTS.md 等）中 NOT 规则净增删条数，≤2 条为稳定；
  - ③反馈包规模 = 反馈条目数，连续轮次须单调递减。
- **退出条件**（命中任一即放弃本范式）：连续 2 轮反馈包不收敛；spec 提取轮耗时 ≥ 该轮强模型实现耗时的 50%（两端耗时试点中均可测）；弱模型盘点输出需人工修正的条目占比 ≥ 50%。

## 后续规划

- **精度由达标到反超**：以最低验收档 F1≈0.92 为起点（与原 CNN+LSTM 同等），将效率提升释放的机时投入调参与消融，目标在新架构上反超 baseline。
- **多档端侧部署落地**：YAML 多档配置已就绪，下一步推进端侧平台部署。
- **资产复用至下一项目**：收敛后的 spec + CLAUDE.md 已带回黄区，同类音频/时序遗留项目重构可直接从规格提取起步，无需从零开始。

---

## 总结

跨区协作是循环而非一次性交接。小数据开发、大数据验证、反馈修正规格，直至收敛。CryDet 的收敛终点：工作量 7–8→1 人月、精度同等（F1≈0.92，达最低验收档）、约 1.3 万行代码 + spec + CLAUDE.md 回域复用。

- 范式起两个作用：在合规墙下打开准入，靠 spec + NOT 规则守住保真。
- 小数据通过不等于大数据通过，spec 保真须人复核。
- 具体的 NOT 约束比"用线性投影"这类泛泛描述有效；重构范围与并行性也由人裁决。
